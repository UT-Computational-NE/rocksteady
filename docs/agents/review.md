# Reviews and merging

- **Accounts.** PRs are opened as `npl436`, which cannot approve its own PRs. `npl436-bot` posts reviews. It has write access, so its approval satisfies the "Protect Main" ruleset, which requires one approving review and allows no bypass.
  - **Posting as the bot.** Pass the bot's token to just that one command: `GH_TOKEN=$(gh auth token --user npl436-bot) gh api --method POST repos/{owner}/{repo}/pulls/<n>/reviews --input review.json`. Pass the token only this way, through `GH_TOKEN=$(…)` on the same command line. Never echo, log or store it, and never put it in a file, a message or a commit.
  - **Keep the active account.** Every session on this machine shares the active `gh` account, so `gh auth switch` would make all of them act as the bot.
  - **Checking who posted:** add `--jq .user.login` to the API call; it prints `npl436-bot` when the bot posted.
- **Requesting a review, or requesting it again:** `gh api --method POST repos/{owner}/{repo}/pulls/<n>/requested_reviewers -f "reviewers[]=npl436-bot"`.
- **Probing a boundary or a tie-break.** When a change defines one (a half-open range, a threshold, which of equal candidates wins), probe it with exact arithmetic (`fractions.Fraction`) on integer and repeated-constant data such as `[0.7] * 53`, where rounding and exact ties actually happen; Gaussian data almost never lands on a boundary or ties. Check that the test's own reference computes exactly too.
- **Probing restatements.** When a change alters what an argument accepts or how a rule works, the old rule is often restated outside the diff. Grep each changed argument's or rule's name in the module docstring, `README.md`, `docs/source/` and the error messages, and check that every sentence found is still true. In PR #102, subtypes' own penalties left the objective, the tie-break paragraph and the README's constraint table untrue.
- **Probing with mutants.** Break each line a diff adds once, run the tests, and restore the file: some test must go red. Besides disabling each guard, drop each coercion or conversion call (`bool(x)` to `x`), swap each reduction for its neighbour (`sum`/`any`, `min`/`max`, `all`/`any`), and shift each index or bound by one. A survivor is a missing test, or an equivalent mutant named with its reason; #101 adds a tool that runs them. In PR #104, a dropped `bool()` and `.sum()` swapped for `.any()` both survived until a review wrote them.
- **Waiting for CI.** GitHub runs no Actions on a PR that conflicts with its base; only Read the Docs reports, as pending. Before waiting on a pushed head's checks, read `gh pr view <n> --json mergeable,headRefOid` until `headRefOid` is the SHA you pushed and `mergeable` is `MERGEABLE` or `CONFLICTING`. Right after a push it reads `UNKNOWN` for a while, or can still describe the previous head: PR #104 read `CONFLICTING` just after its conflicts were merged and pushed. When it is `CONFLICTING`, merge the base into the branch first. Read the results with `gh pr checks <n> --json name,bucket`; the plain table splits names such as `test (3.10)` into columns.
- **Merging.** Merge only when the user asks, with a merge commit, not a squash: `gh pr merge <n> --merge --subject "Merge #<n>: <title>"`. The base may have moved since the approved head's CI ran, so first test-merge with the base as it is now: `git fetch origin`, `git worktree add --detach <dir> origin/<base>`, `git -C <dir> merge <head>`, run `tools/check.sh` there, then remove `<dir>`.
- **Stacked PRs.** Before deleting a merged parent's branch, retarget the child to `main` with `gh pr edit <child> --base main`. Deleting the parent's branch first closes the child.
- **After a merge,** first retarget any stacked child PR (see above). Then remove the worktree (`git worktree remove`) and delete the branch locally and on the remote (`git branch -d`, `git push origin --delete`).
